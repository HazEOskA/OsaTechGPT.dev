OSA Execution Force: authority before mutation

Execution Force controls the path from task to action. Policy, repository, scope, source provenance and the exact downstream payload are bound before a mutation-capable runtime can proceed.

CLAIM ≠ PROOF. No evidence = UNKNOWN.
Authority path

Policy is upstream of execution

Execution Force separates authority from the downstream engine. GODMODE V3 resolves the policy and card, binds the task to repository, scope, source SHA and payload, then authorizes the exact RuntimeV2 execution path.

TASK → GODMODE V3 → CARD / POLICY → bound repo + scope + source SHA + payload digest → RuntimeV2 → host action → evidence / verification
Fail closed

Runtime state alone cannot open mutation authority

The documented P0 invariants deny a direct RuntimeV2 mutation path before V3 authorization, reject modified policy payloads, prevent scope widening and require an exact source commit SHA for provenance.

The committed registry contains 150 operational cards across 14 engineering domains. The catalog is a policy surface, not evidence by itself; the authority wiring is tested separately.

Proof boundary

P0 proves wiring, not universal production readiness

The repository publishes a dedicated authority workflow and launcher provenance proof for the project-scoped Claude Code path. It also states what is not claimed: P0 is not a universal enforcement proof across every host and does not establish production readiness.
