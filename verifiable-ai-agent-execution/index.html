Research · Verifiable Execution

Verifiable AI agent execution: from output to independent proof

An AI agent can produce a convincing result without proving how the work was executed. Verifiable execution separates the claim, the evidence and the verifier.

CLAIM ≠ PROOF. No evidence = UNKNOWN.
Core concept

What verifiable execution means

Verifiable AI agent execution means an agent's result is accompanied by evidence that can be checked independently from the agent's own narrative. The system does not stop at “the model returned an answer.” It records a bounded execution and produces enough evidence to validate defined properties of that run.

This is narrower and more useful than the vague claim that an agent is “trustworthy.” Verification should always state what was verified, by which checks and under which trust boundary.

Agent claim ≠ execution evidence ≠ independent verification A useful system keeps these layers separate.
Problem

Why an agent saying “done” is insufficient

Modern agents can generate code, modify files, call external tools and coordinate multi-step workflows. That capability creates a verification problem. A final answer can be correct while the process violated constraints, or it can look plausible while required work never happened.

Three common substitutes for proof are weak when used alone:

SignalUseful forWhat it does not prove alone
Agent responseIntent and explanationThat required actions actually occurred or checks passed.
Application logsDebugging and observabilityThat the evidence set is complete, bound to one mission and resistant to unnoticed mutation.
Screenshot / demoHuman review of a visible stateWhich execution produced that state or whether hidden requirements passed.
Evidence path

A practical verification pipeline

  1. Define the mission boundary. State what the run is allowed and expected to do.
  2. Capture execution evidence. Record relevant events and artifacts during the run.
  3. Run deterministic checks. Validate properties that do not depend on the model declaring itself successful.
  4. Bind the evidence. Make later mutation detectable through hashes or an equivalent integrity mechanism.
  5. Produce a proof package. Keep evidence and verification metadata together.
  6. Verify independently. Re-run integrity and requirement checks outside the agent's own reasoning loop.
  7. Return an explicit status. Verified, failed or unknown should be distinguishable.

APR implements this direction with mission manifests, deterministic checks, an event chain, a Merkle root, a Proof Bundle and an independent verifier.

Governance

Verification is strongest when paired with control

Evidence after execution is valuable, but mature agent systems also need runtime boundaries before and during execution. That includes explicit tool permissions, capability limits, approval gates, scoped credentials and clear failure behavior.

This creates two complementary layers:

CONTROL What may the agent do? PROOF What evidence shows what actually happened?

Governance without evidence can become policy theater. Evidence without control can document a bad action after it happened. The useful architecture connects both.

Evaluation

Questions to ask any “verifiable agent” system

  • What exactly is the unit of execution being verified?
  • Which checks are deterministic and which depend on another model?
  • Can evidence from two different runs be accidentally mixed?
  • How is evidence integrity checked after the run?
  • Can a verifier run independently from the agent?
  • What happens when evidence is missing?
  • Does the product distinguish local verification from external anchoring or hardware-backed trust?
  • Can a tampered copy be detected in a reproducible test?

If a system cannot answer those questions precisely, “verified” may be a label rather than an engineering property.
